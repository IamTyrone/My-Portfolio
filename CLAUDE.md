# Working in this repo

This is Tyrone's portfolio. Every word of prose in it is published as his own
writing, so the bar is simple: a reader should never be able to tell a machine
touched it.

## Writing rules

These are hard rules, not preferences.

**Never use double hyphens (`--`), em dashes (`—`) or en dashes (`–`) in prose.**
Rewrite with a comma, a colon, a full stop, or brackets. If a sentence only
works with a dash, the sentence needs restructuring. Check before finishing:

```bash
grep -rn '—\|–\|--' content/ lib/projects/ lib/blog/
```

Hyphenated words (`full-stack`, `server-side`) are fine. Command flags in
terminal-styled UI copy, like `--fullstack` in the project filters, are fine:
they are code, not prose.

**Never say or hint that anything here was written or generated by AI.** No
disclaimers, no "generated with", no hedging about authorship.

**Avoid the tells.** In rough order of how badly they give the game away:

- The dash habit above. It is the single loudest signal.
- "It's not just X, it's Y" and "not only X but also Y" constructions.
- Rule-of-three abstract adjectives: "robust, scalable and maintainable",
  "fast, secure and reliable". Pick one concrete claim instead.
- Openers like "In today's fast-paced world", "In the ever-evolving landscape
  of", "Picture this", or a rhetorical question.
- Vocabulary: delve, leverage, utilise, seamless, robust, cutting-edge,
  game-changer, unlock, elevate, empower, journey, testament to, deep dive,
  landscape, realm, tapestry, "at its core", "under the hood" as filler.
- A closing paragraph that restates the whole piece. End on a real point, or a
  joke, and stop.
- Uniform rhythm: every paragraph the same length, every sentence the same
  shape. Real writing is lumpy. Let a three word sentence sit next to a long one.
- Superlatives with no number attached. "Massively scalable" says nothing;
  "14,000 lines across 145 files" says something.
- Bolded label lists and emoji bullets inside what should be prose.
- Flattery and hype about the work. State what it does and what it cost.

**Write like the existing entries.** First person, dry, specific, happy to name
the annoying bug or the thing that nearly went wrong. Concrete numbers, real
file names, actual trade-offs. Jokes are welcome and should be load bearing,
not decorative.

**Do not tidy his voice.** Existing copy has typos, contractions without
apostrophes and British spellings sitting next to American ones. Leave them
unless asked. Rewriting his phrasing into neutral prose is worse than a typo.

## Content layout

Prose and metadata live outside the page components, so nothing large ships to
the browser.

**Projects**

- `lib/projects/projects.ts` is the single source of truth for every project
  card: id, title, `summary`, tags, category, links, `featured`. The home page
  and `/projects` both read it, so there is no second copy to drift.
- `lib/projects/details.ts` holds detail-page-only data for the projects that
  have a write-up: `intro`, image, timeline, team, status, features, techStack,
  challenges, learnings, and the `file` naming its markdown.
- `content/projects/<slug>.md` is the write-up body, plain paragraphs separated
  by blank lines, read on the server by `lib/projects/content.ts`.
- `lib/projects/app-links.ts` holds store listings for projects with mobile
  apps, keyed by project id, with an optional square `icon`.
- Adding a write-up means: a markdown file, a `details.ts` entry, an image.
  `generateStaticParams` picks it up from the `projectDetails` keys, so the new
  page prerenders with no further wiring.
- Projects with no `details.ts` entry deliberately 404 on `/projects/<id>`.
  Their cards still link there. Fix that by gating the link on a small id list,
  never by importing `details.ts` into a client component, which would drag the
  detail data back into the bundle.

**Blog**

Same shape: `lib/blog/posts.ts` for metadata, `content/blog/*.md` for bodies,
`lib/blog/content.ts` to read them, `lib/markdown.ts` to render.

**Images**

`public/img/projects/<project>/<name>.webp`. Screenshots are captured at
1600x900 for the 16:9 detail hero and converted to WebP, which keeps them under
about 90 KB. Use headless Chrome:

```bash
google-chrome --headless --disable-gpu --no-sandbox --hide-scrollbars \
  --window-size=1600,900 --virtual-time-budget=12000 \
  --screenshot=out.png https://example.com
```

Then convert with Pillow (`quality=84, method=6`). Prefer a local asset to
hotlinking someone else's CDN. Set `imageFit: "contain"` for logos and artwork
that must not be cropped.

## Code notes

- `types/framer-motion-react19.d.ts` restores `ReactHTML` and
  `DetailedHTMLFactory`, which `@types/react` 19 removed and framer-motion 10
  still needs to type `motion.*` props. Without it every motion element throws
  TS2322 on `className`. Delete the file when framer-motion is upgraded to
  v11 or newer.
- `next.config.js` still sets `typescript.ignoreBuildErrors` and
  `eslint.ignoreDuringBuilds`. The repo currently typechecks clean, so run
  `npx tsc --noEmit` yourself before calling a change done. A green
  `next build` is not proof of anything.
- Keep the terminal aesthetic: `terminal-window`, `terminal-titlebar`,
  `terminal-body`, `text-terminal-green`, `text-evil-red`, `text-hack-cyan`,
  and the `$ command` phrasing in UI labels.
- Tech tags render through `SkillChip`. `lib/tech-icons.tsx` maps a normalised
  tag name to a logo and falls back to a neutral spark, so check a new tag has
  a real entry before using it, or expect a generic chip.

## Before finishing

1. `npx tsc --noEmit` reports zero errors.
2. `npx next build` succeeds, and the route table shows what you expect,
   including anything that should be prerendered.
3. The dash grep above comes back empty.
4. New prose reads like the neighbouring entries, not like a press release.
